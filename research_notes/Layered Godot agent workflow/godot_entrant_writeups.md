# First-hand write-ups from Godot entrants and Godot agent post-mortems (2025–2026)

Scope note. Collected 2026-11-24. ziva.sh, itch.io, slapjam.ai, top3d.ai, saschb2b.com, dev.to, note.com and raw.githubusercontent.com were fetched with curl through the proxy (WebFetch could not resolve hosts). itch.io rate-limited (HTTP 429) many requests. Because of that, the pages for **Fire keeper** (Micro Jam 063 #1), **Follow the Wheat** (Micro Jam 059 #2) and the **Ziva Game Jam** itch page were never read. Their entries below come only from Ziva's blog, a secondary and vendor source. The GitHub API refused the innollia repo, but raw.githubusercontent.com served its docs.

Overall finding: **few first-hand, detailed workflow write-ups from top-placed Godot AI-jam entrants exist.** Most top entries only credit their tools on the game page. Only two placed Godot entries left real workflow records: Keep It Crispy (devlog) and Shrinestone (public repo docs). Several podium entries in AI jams were not Godot at all (Three.js, Phaser). These are noted below as comparators.

## What tool combinations did top Godot entrants use, and what did they report as decisive?

### Takeaway
The placed Godot entries I could verify used Claude Code (Opus 5.5) as the main coder on Godot 4.7. A second model, Codex/GPT image generation, did 2D art. Blender, driven by Python scripts, produced the 3D. None of the placed entrants named a Godot MCP server. What they called decisive was a fast human-playtest loop on the target device (Keep It Crispy). Shrinestone instead leaned on durable written handoff docs, a headless smoke test and scripted test scenes. Outside jams, the decisive tools were MCP servers that let the agent run the game, send input and take screenshots (godot-mcp, Ziva).

### Cited Findings

**Account 1: Keep It Crispy, juslangit (Luqman Hakeem). Slapjam #1 (theme Castles, Sept 2026), 1st place of 141 rated entries, $250. Devlog posted ~2026-09-30.**
- Placement: #1 at 4.267 combined (Fun 4.000 / Visual 4.200 / Theme 4.600), from 5 ratings — [Slapjam #1 results](https://slapjam.ai/jams/slapjam-1/)
- Genre: 3D arcade action. You fly a dragon by tilting the phone and burn a castle; it has a wizard boss and plays on mobile in portrait — [game page](https://juslangit.itch.io/keep-it-crispy)
- Engine and tools: "Engine: Godot 4.7 · 3D modelling: Blender 5.2". Claude Code (Claude Opus 5.5) did "Code, gameplay, effects, and all 3D models … built in Blender by script". Codex (OpenAI) image generation did concept art, title, logo, UI and icons. Freesound/Kenney CC0 supplied the audio — [game page](https://juslangit.itch.io/keep-it-crispy)
- Human role: "I'm a 3D artist and teacher, so I directed and playtested, and let two AI tools do the heavy lifting". Claude Code also "handled the sound and the itch.io uploads" — [devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)
- Loop: "I played on my iPhone, said what felt wrong ('the fire isn't scary enough', 'too hard for kids', 'I can't see the dragon behind this panel'), and it got fixed, often within minutes." Built "in one day" — [devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)
- Art pipeline: Codex painted a concept sheet first, "and everything else followed that look". The 3D models come from Blender scripts that fuse primitive shapes, smooth them, decimate them, paint them and add a 12-bone rig. As a result "any of them can be changed and rebuilt in seconds". One shared dragon body gets recoloured by a shader — [devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)
- Failures and recoveries, all platform or web-export issues rather than code-structure bugs. Phone angle readings "go haywire" when the phone is held upright; the fix steered from the gravity vector. Tilt flipped the screen to landscape; full steer now comes at 25°, and the game pauses if the screen rotates. iPhone motion sensors work only over https, so every test ran through an https tunnel. Inside the itch iframe the iPhone gave no motion at all; the fix opens the game as its own page on first tap. Firefox Android had no angle readings; the fix fell back to the accelerometer. In the phone web renderer, flat flame sprites drew a black circle and were replaced with low-poly blobs. Web audio needed a first-tap wake. The first Android build was unplayable; LOW/MEDIUM/HIGH graphics settings, including half-resolution 3D, fixed it — [devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)
- Not mentioned: no MCP server, rules file or template is named, and no time split is given beyond "one day".

**Account 2: Shrinestone ("Rock and Stone"), innollia, a Korean team that calls itself "100% vibe coding". Slapjam #2 (theme Speed, Oct 29–31 2026), 3rd of 211 rated entries. Published ~2026-11-01. Repo docs dated 2026-10-30/31.**
- Placement: 3rd, Overall 3.750 — [Slapjam #2 results](https://slapjam.ai/jams/slapjam-2/)
- Genre: 3D momentum/rolling action across 11 zones, mobile portrait — [game page](https://innollia.itch.io/shrinestone)
- Tools as disclosed: "Godot 4.7, Blender, Python (Pillow, numpy, scipy), nkido (MIT, sound synthesis), Claude (Anthropic), Codex (OpenAI)". GPT generated the textures and stone UI images. "Code, planning and text were developed with Claude and Codex." — [game page](https://innollia.itch.io/shrinestone)
- Fixed-in-advance harness, from the repo's root `CLAUDE.md`. The human ("Pai") calls a Claude worker bot from a Discord thread. The bot reads the last 30 messages with `tools/discord.py`, does the work, commits and pushes, and replies with a play link (GitHub Pages) in under 1,500 chars. It posts 3–8 progress lines per call. Prohibitions: printing secrets, @mentions, and writing outside the folder — [CLAUDE.md](https://raw.githubusercontent.com/innollia/pai-games/main/CLAUDE.md)
- Handoff discipline, from the per-game `README.md`. It is at version v27, and "A new session reads from the 'Handoff (v26)' section first". It lists what changed v15–v26, "things the user pointed out but not yet fixed (do first)", and a section titled "Decisions made by the user (don't ask again)". Examples: no generic "BOOM! +40" popups, no collectibles, no separate tutorial, no rounded UI, and keep the underground spatially continuous (translated from Korean) — [README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)
- Verification harness: a headless smoke test, `Godot_v4.7.2-stable_win64_console.exe --headless --path . --fixed-fps 60 -s tools/smoke.gd -- boulder`, runs before every push. A set of scripted test scenes lives in `work/` (not in git): `under_test` (no input), `under_steer_test`, `updraft_test`, `cliff_test`, `fork_test`, `count_test` (object count per zone), `warp_test`, `pillar_test`, and `perf_test` (fps and draw calls per zone at 540x960). A `SUBMIT_CHECKLIST.md` is kept, and "itch upload is done by the user" — [README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)
- Human role: design taste and veto. The user dislikes "punish-by-death" fixes. One example: falling without HOLD "dies out of nowhere", which v27 fixed by rolling over the roof slowed to ×0.45. The user also does the phone checks; several items read "needs phone confirmation" — [README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)
- Art pipeline failures, from `ART_LOG.md`. Nested Codex texture invocations failed 10 times with "failed to initialize in-process app-server client / access denied (os error 5)". A GPT request with reference images failed with "network error". The text-only retry worked. GPT "preserved island topology but shifted/scaled it", so a Python `align_textures.py` re-fits the paint to UV layouts. Blender 5.2 runs headless to normalize the meshes. "Final source atlases were visually inspected as image files; no game screenshots were taken." — [ART_LOG](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/ART_LOG.md)
- Performance work recorded in the handoff: the road is built in 16 m chunks, one chunk per frame through a queue, with MultiMesh batching ("draw calls about halved") — [README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)

### Inferences
- Among placed AI-jam Godot entries, the common stack is Claude Code (Opus-class) for code, a separate image model (Codex/GPT) for 2D art, and Blender driven by Python for 3D. Neither placed entry with a write-up said it used a Godot MCP server. Their verification ran through headless Godot scripts (Shrinestone) or human playtests on phone (Keep It Crispy).
- Placed entries put 3D art behind scripts ("rebuild in seconds"), so art can be iterated by the agent. This is the same "generate from data" principle bomb-it-5 already uses.
- Shrinestone's README pattern is a durable answer to context loss across sessions, and Mormon Trail and zizochan both report context loss. The pattern has three parts: a handoff section, a list of "user decisions, don't ask again", and an "open user complaints first" list.

- Fire keeper and Follow the Wheat pages and devlogs could not be read (itch 429), so their tools, engine version and workflow are unverified beyond Ziva's blog.
- The Ziva Game Jam itch page returned 429; I found no results or winner write-ups for it.
- Slapjam #2 4th/5th place and Slapjam #1 5th place engines were not checked.
- No entrant reported a time split beyond "one day" (Keep It Crispy) or "~7 hours" (Exonix).

## What did they keep for the human?

### Takeaway
In every account, design direction, feel and playtesting on the real device stayed with the human, along with veto over "fixes" that hurt the game. Upload and submission also stayed human in Shrinestone; in Keep It Crispy Claude handled the uploads. Humans also took over short manual art fixes and made the call to step in when the agent was looping.

- "I directed and playtested" — playing on iPhone and voicing what felt wrong — [Keep It Crispy devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)
- Shrinestone recorded user decisions as standing constraints and left phone confirmation and the itch upload to the user ("itch upload is done by the user") — [README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)

### Inferences
- Humans hand-wrote the ground-truth specs (rules, design decisions) and did not let the agent edit them. Agents edited everything downstream of those specs.

### Gaps
- No account measured how many human hours went to playtesting versus prompting.

## What failures recur (node paths, .tscn corruption, signals, Godot 3/4 API, visual bugs, feel)?

### Takeaway
The failures that recur most often are: feel and balance the agent cannot perceive; agents bypassing Godot's scene system for one giant procedural script; context loss and regressions across sessions; web/mobile export quirks; and validation that checks syntax but not semantics. I found **no first-hand report of .tscn corruption, broken node paths or a Godot 3/4 API mix-up** in these 2025–2026 accounts. The closest reports are wrong signal signatures and nonexistent methods getting past syntax-only validation.

### Cited Findings
- Feel/balance: "Balance By Theory, Not Feel … a 30-second playtest by a human would reveal instantly" — [saschb2b.com](https://saschb2b.com/blog/godot-mcp-ai-game-creation); "AI doesn't understand what is correct as a game" (translated) — [zizochan](https://note.com/zizochan/n/n7a5c52819bba); the Ziva Playtest Agent "does not tell you whether the game is fun" — [Slapjam review](https://slapjam.ai/news/ziva-review-godot-ai-agent/)

A commenter says the agent "often favours something complex in a script, when there could be a simpler solution using scenes" — [dev.to comment](https://dev.to/datadeer/part-1-building-an-rts-in-godot-what-if-claude-writes-all-code-49f9). - Recoveries that worked: small increments verified one at a time ([Exonix](https://www.top3d.ai/learn/claude-godot-mcp-3d-game), [Mormon Trail](https://russperry.itch.io/the-mormon-trail-rpg/devlog/1133249/dec-26-devlog)); a headless smoke test plus scripted, input-free test scenes ([Shrinestone](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)); an agent-built runtime driver with screenshots ([Iskamag](https://iskamag.itch.io/chrono/devlog/1608657/to-vibe-a-gamedev-a-first-experience)); short manual human interventions ([Exonix](https://www.top3d.ai/learn/claude-godot-mcp-3d-game))

### Inferences
- The failures that matter most for a port like bomb-it-5 are scene-system bypass and semantic, not syntactic, errors. The defenses that fit them are headless runtime tests, scripted input scenarios, and rules that require real scenes.
- Godot 3/4 API confusion did not appear in 2026 accounts. The only engine-grounding complaint, Mr Phil Games, is from mid-2025.

### Gaps
- None of the accounts gave a first-hand description of .tscn corruption or broken node paths. I can't tell whether they are rare or just unreported.
- The secondary dev.to article ([xu_xu](https://dev.to/xu_xu_b2179aa8fc958d531d1/claude-code-is-writing-your-godot-games-heres-the-hidden-cost-nobody-talks-about-4a7n)) only comments on someone else's Qiita tutorial, so it was not counted as first-hand.
