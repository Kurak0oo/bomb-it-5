# Godot plugins give agents eyes, not judgment

Godot agent skills and plugins will not solve the problems that derailed this project, because most of those problems come from the process, not from missing tools. The two DeepSeek Harness (dsh) reference plugins show this clearly. **akira399/dsh-godot-skill is a 444-line static Godot 4 cheat sheet that addresses none of the listed problems**, and its "AI plans, builds and exports on its own" workflow pushes against the project's rule that only the owner closes UI and art work. **Smalldy/godot-bridge does address one real gap**: it gives the agent runtime eyes and hands (single-frame screenshots, input injection, a live scene tree and UI rectangles, property and shader tweaks, bounded headless runs). Every one of its capabilities is also available to Claude Code, Codex and Cursor through MCP servers, starting with its own upstream, tugcantopaloglu/godot-mcp. No plugin in either ecosystem gates acceptance on a human, keeps docs short, carries memory across sessions, or diffs a running game against an external reference such as SWF data. Competitions and benchmarks from 2025–2026 point the same way: agents do best on core mechanics and worst on UI, 2D art and presentation, and executable state checks judge behavior far better than a vision-model judge. A fixed, genre-independent Godot workflow exists only as a *verification pipeline*, not as a content or design process. A grid-based remake with its original as an oracle is the case that pipeline fits best. The highest-value next steps for this project are therefore to enforce the owner gate in tooling, keep the node-diff comparison loop as the main check, and add a light runtime MCP plus Godot's own embedded game view as the live playground.

## Two dsh plugins cover one of six problems between them

DeepSeek Harness is an MIT-licensed agent harness from DeepSeek AI, still a developer preview that warns of breaking changes, built on the Cordis "everything is a plugin" framework ([deepseek-harness README](https://github.com/deepseek-ai/deepseek-harness)). Its skills use the same `SKILL.md` progressive-disclosure format as Claude Code and Codex: a name and description catalog, with the full body loaded on demand ([DSH skill-system note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/feature/2026-07-05-skill-system.md)). It also ships an MCP *client* that registers each MCP server's tools as native tools ([DSH MCP client note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/feature/2026-07-07-mcp-client-plugin.md)). So a skill-only dsh plugin moves to other harnesses by copying one file, while a native dsh tool plugin, a Node module that calls `ctx.tools.register`, does not move at all.

**dsh-godot-skill** is that skill-only case. It is a single Chinese-language skill condensed from Godot's official feature list. It covers core concepts, a project layout, renderer choice, a 20-domain API cheat sheet, a seven-stage "design → scaffold → prototype → content → polish → test → export" workflow, code templates and an error table. About 80 lines of JS register it at runtime ([repo](https://github.com/akira399/dsh-godot-skill); [SKILL.md](https://github.com/akira399/dsh-godot-skill/blob/main/.dsh/skills/godot-4-development/SKILL.md)). Its testing advice stops at `godot --path . --debug`, `print()` and the remote inspector. It pins no engine version and has had no commits since 28 August 2026. Frontier models already know this material: on flockbay's 15-task Godot 4.7 API suite, Claude Opus 5.5, Sonnet 5.5 and GPT-6.1 all scored 15/15 ([godot-llm-bench](https://raw.githubusercontent.com/flockbay/godot-llm-bench/HEAD/README.md)), and Claude Opus 4.8 scored 300/300 on the GDScript-Eval v2 tasks ([estragon](https://raw.githubusercontent.com/blugart-dev/estragon/HEAD/README.md)). A generic Godot knowledge skill therefore adds little for a frontier model, and nothing specific to a faithful AS3 port.

**godot-bridge** is the substantive one. It launches the game, injects an autoload (`McpInteractionServer`, loopback port 9090, newline-delimited JSON) and exposes 17 `godot_*` tools. With them an agent can take a viewport PNG, press keys and InputMap actions, read the scene tree and UI elements with positions and sizes, get and set properties, call methods, run `eval`, change `time_scale`, pause, set shader parameters, compile-check GDScript, and run bounded headless sessions ([README](https://github.com/Smalldy/godot-bridge); [server source](https://github.com/Smalldy/godot-bridge/blob/main/plugin/mcp_interaction_server.gd)). Its most useful contribution is a set of measured headless pitfalls. An `eval` syntax error under `-d` drops Godot into an interactive `debug>` prompt that printed 12,089 lines (1.78 MB) in 3 seconds. Headless scenes without `--quit-after` loop forever. Version-manager shims orphan the real process. A sandboxed shell crashes Godot on `user://` log writes ([CHANGELOG 0.2.1](https://github.com/Smalldy/godot-bridge/blob/main/CHANGELOG.md)). It is young (v0.1.0 to v0.2.1 between August and October 2026, 60 stars) and was measured on Godot 4.7.2, not 4.5. All of its GDScript is vendored from tugcantopaloglu/godot-mcp, which is an MCP server ([tugcantopaloglu/godot-mcp](https://github.com/tugcantopaloglu/godot-mcp)).

| Problem in this project | dsh-godot-skill | godot-bridge |
| --- | --- | --- |
| Agents closed UI/art work on self-referential checks | No; its autonomous workflow makes it worse | No; screenshots let the agent judge itself more, with no human gate and no reference diff |
| Slow pixel loops and huge recordings (193 MB of goldens) | No | Partly: one frame on demand plus `pause`/`time_scale`; no deterministic frame-advance and no golden diff |
| Docs bloated into cross-session memory | No; it is itself a long doc | No |
| Context lost between sessions | No | No; `serialize_state` dumps game state, not agent memory |
| No live playground for art and in-game effects | No | Partly: a running game you can poke, but changes are not written back and nothing is shown to the owner |
| Headless test traps | Barely | Strong |

The pattern is clear. A Godot bridge solves *perception*: whether the agent can see and drive the game. The failures this project recorded were about *authority* (who decides a screen is right), *reference* (right compared with what) and *memory* (what the next session knows). Tools cannot fix those by seeing more. A bridge that lets an agent screenshot its own menu and declare it good automates the exact failure described in `docs/development.md`: checks that "only compared the layout tables with themselves."

## Every capability has an MCP equivalent outside dsh

Nothing in either dsh plugin is exclusive to dsh. The Godot MCP ecosystem is crowded, with dozens of overlapping servers offering 100–190 tools each. The servers that matter for this project split into three groups, and the Godot version pin decides between them.

| Tool | License / cost | Godot | What it adds | Fit for this project |
| --- | --- | --- | --- | --- |
| [Erodenn/godot-mcp-runtime](https://raw.githubusercontent.com/Erodenn/godot-mcp-runtime/HEAD/README.md) | MIT, free | **4.5+** | No committed addon; injects a bridge on `run_project`; screenshots with a `likelyBlank` verdict, batched input, UI discovery, live GDScript, `render_movie` blank/moving check | Best fit: matches the 4.5 pin and leaves `project.godot` alone |
| [tugcantopaloglu/godot-mcp](https://github.com/tugcantopaloglu/godot-mcp) | MIT, free | tested on 4.7 | 157 tools, same protocol as godot-bridge; needs a committed autoload | Works, but the autoload (with `eval`) must stay out of export presets |
| [hi-godot/godot-ai](https://raw.githubusercontent.com/hi-godot/godot-ai/HEAD/README.md) | MIT, free | **4.7+ only** | Most active (3.7k stars, pushed 2026-11-22); editor-attached; parse-validates GDScript; refuses writes to `project.godot` | Ruled out by the 4.5 pin |
| [youichi-uda/godot-mcp-pro](https://raw.githubusercontent.com/youichi-uda/godot-mcp-pro/HEAD/README.md) | Paid server | 4.x | Game screenshots, `compare_screenshots`, `capture_frames`, input sequences with frame delays, record/replay | Strongest capture features, but closed-source and a recurring dependency |
| [Coding-Solo/godot-mcp](https://raw.githubusercontent.com/Coding-Solo/godot-mcp/HEAD/README.md) | MIT, free | 4.x | Most stars (6.7k) but only launches the game and reads logs; last push April 2026 | Too thin |

Skill and rule packs have grown faster than the tools. Claude-Code-Game-Studios has 40.7k stars for "49 AI agents, 75 workflow skills" of generic studio role-play. awesome-gamedev-agent-skills (10.5k) is pinned to Godot 4.7.2. GodotPrompter (985) ships 59 skills, including GUT and gdUnit4 testing, to Claude Code, Codex, Cursor and others ([godot_ai_tooling sources](https://raw.githubusercontent.com/jame581/GodotPrompter/HEAD/README.md); [awesome-gamedev-agent-skills](https://raw.githubusercontent.com/gamedev-skills/awesome-gamedev-agent-skills/HEAD/README.md)). These packs mainly fight Godot 3-versus-4 confusion, which frontier models have largely outgrown. Their default stance, the agent builds and decides, conflicts with this project's "translate, don't reinvent" and owner-closes-UI rules. The most instructive is htdt/godogen (7.4k stars). Its early versions scripted the agent through PLAN.md, STRUCTURE.md, a decomposer and an architect; the current version deliberately "doesn't plan for it, check its work or decide when it's done" and tells the user to ask for a screenshot or video whenever they want to see progress ([godogen README](https://raw.githubusercontent.com/htdt/godogen/HEAD/README.md)). That is the same conclusion this project reached at its restart: heavy process docs did not make the agent reliable, and a human look is the real acceptance step.

Even the tool authors say the human remains necessary. godot-mcp-runtime's README warns that it "doesn't catch the subtle feel issues that only a human notices" ([README](https://raw.githubusercontent.com/Erodenn/godot-mcp-runtime/HEAD/README.md)). No surveyed tool documents tolerance-based diffing against an external reference such as SWF frames or display lists. For a parity port, that comparison loop has to be built by the project, and this project has already built it.

The tooling also has practical traps, mostly around headless runs. Headless Godot 4 uses a dummy renderer that produces no pixels, so screenshots need a display server or Xvfb ([Godot Q&A](https://ask.godotengine.org/150510/godot-headless-not-same-godot-window-cant-render-the-backend)). A forum post measured on Godot 4.5–4.7.2 found GUT printing "All tests passed!" with exit code 0 when some of its own scripts failed to load ([Godot forum](https://forum.godotengine.org/t/things-that-exit-0-in-godot-4-headless-even-though-they-failed-measured-reproducible/145990)). Practitioners also report malformed `.tscn` files and stale editor caches after agents write scene text directly ([Godot Asset Library](https://godotengine.org/asset-library/asset/5482); [Fennara on dev.to](https://dev.to/fennaraofficial/i-tested-popular-godot-mcps-by-migrating-a-godot-36-project-to-godot-46-34d2)). This project's generated-scene converter already avoids most of the last problem, because scenes are produced from SWF data rather than edited by hand.

## Benchmarks and jams agree that presentation is where agents fail

The 2026 benchmarks converged on Godot because it is open source, scriptable headless and text-serialized, which makes it automatically gradable. Their results consistently show where agents break. **GameDevBench** (ICML 2026) found the best agent at 53.8% overall but only about 33% on 2D graphics and animation and 32% on UI, with screenshot and video feedback adding roughly ten points (GPT-5.4 from 41.1% to 52.0%) ([arXiv 2602.11103](https://arxiv.org/html/2602.11103); [ICML](https://icml.cc/virtual/2026/poster/64919)). **GameCraft-Bench** (June 2026, 140 Godot tasks across 15 game families) put Claude Code with Opus 4.7 on top at 41.46%. Its best agent scored 55.34% on core mechanics but only 36.86% on art and presentation, and the authors note that agents "can often produce runnable game-like artifacts" without realizing the requested visual state ([arXiv 2606.17861](https://arxiv.org/abs/2606.17861); [project site](https://tongxuluo.github.io/gamecraft-bench-website/)). This is the profile this project lived through: logic checks against the reference player held up, while UI and art passed checks that could not judge them.

Two newer benchmarks show *how* to judge. **SWE-Game** (247 tasks on 41 Godot reference games) found that executable checks reached 92.59% balanced accuracy on human-labeled behaviors, against 78.41% for a video-based vision-model judge ([arXiv 2609.33678](https://arxiv.org/abs/2609.33678)). **GameLogicBench** scores state and event history at every simulation tick with no language model in the scoring path. In its ablation, checking only the terminal state let injected faults escape on 34 of 36 tasks ([arXiv 2609.21562](https://arxiv.org/abs/2609.21562v2); [GitHub](https://github.com/NJU-LINK/GameLogicBench)). It also found success falling as scope grows from isolated mechanics to repository-scale features, and the same model scoring between 26.4% and 44.4% depending on scaffold. These figures come from search snippets of the papers, not from the PDFs, so treat exact numbers as reported rather than verified. The direction is consistent across all of them: verify with structured state first, pixels second, and a vision-model "looks right" last. This project's choice to diff display-list nodes (path, position, scale, frame, visibility) before SSIM and ΔE matches that ordering exactly.

The jams tell a different story about where agent-built games succeed. The large AI-built game event is Pieter Levels' web-only Vibe Coding Game Jam: 945 games in 2026 under a 90%+ AI-code rule, sponsored by Cursor ([Summer Engine](https://www.summerengine.com/blog/cursor-vibe-jam-2026-guide); [Colyseus](https://colyseus.io/blog/vibe-jam-2026/)). Successful agent-built games cluster on three.js, PIXI and Phaser, where agent and player share one fast-feedback runtime ([Simon Willison](https://simonwillison.net/2026/Oct/28/vibe-game-development/); [Hugging Face](https://huggingface.co/blog/vibegame)). Godot's agent jams are small and vendor-run. The Ziva Game Jam required Ziva and Godot only, and Ziva reports 81 declared entries across its Micro Jam bracket ([itch.io](https://itch.io/jam/ziva-game-jam); [Ziva blog](https://ziva.sh/blogs/godot-game-jam-winners)). The main community Godot jam, Godot Wild Jam, bans AI code and assets outright ([itch.io GWJ 90](https://itch.io/jam/godot-wild-jam-90)), and the Godot Foundation moved in mid-2026 to bar AI-authored contributions to the engine itself ([GamingOnLinux](https://gamingonlinux.com/2026/07/godot-engine-to-get-stricter-on-ai-contributed-code)). That policy does not restrict game projects. Epic's 2026 AI MegaJam on Unreal drew 2,782 submissions after Epic walked back its rule that AI use was mandatory, and an AI-free game topped the popularity ranking ([PC Gamer](https://www.pcgamer.com/software/ai/epic-announces-game-jam-where-you-have-to-use-ai/?type=Games); [Automaton](https://automaton-media.com/en/news/ai-free-fih-aura-farming-game-tops-popularity-ranking-in-epic-games-major-ai-game-jam/)). Jam winners show tight scope, a human steering and playtesting, and little reliance on one-shot generation. None of them attempts a pixel-faithful remake, so jams offer almost no evidence for this project's hardest requirement.

## A fixed workflow generalizes only as a verification pipeline

No published work shows one fixed workflow succeeding across all genres. What does transfer is a verification spine, supported by benchmark and studio evidence. Separate the simulation from presentation, with a fixed tick and one seeded RNG. Unit-test rules headless. Replay scripted or recorded inputs with per-tick state assertions. Keep visual goldens that only an approved change may regenerate. Put a human acceptance gate on every vertical slice. Riot built League of Legends determinism for "fast, repeatable tests driven from a set of recordable inputs" and debugs by finding the first divergence ([Riot Tech](https://technology.riotgames.com/node/67)). Rare's Sea of Thieves suite is mostly unit tests plus integration tests run before every check-in, and the approach later carried over to Minecraft ([Game Developer](https://gamedeveloper.com/design/how-rare-automates-testing-for-ai-and-more-in-sea-of-thieves-part-4-of-4-); [GDC Vault](https://gdcvault.com/play/1027345/Lessons-Learned-in-Adapting-the)).

The spine breaks wherever correctness is not a state predicate. Game feel and real-time timing defeat GUI playtester agents, especially in platformers ([Play2Code](https://arxiv.org/html/2605.28258v1)). Godot's float physics is not deterministic ([GDQuest](https://www.gdquest.com/library/glossary/deterministic_simulation)), so physics-heavy games need tolerance-based replays or a custom simulation. Multiplayer needs its own netcode design and multi-process tests ([Factorio wiki](https://wiki.factorio.com/Desynchronization)). Content-heavy and narrative games are limited by the content-depth scores, where agents are weakest. A Godot metroidvania attempt was abandoned after about 40 hours when grid-size changes and the player controller overwhelmed the agent ([Godot forum](https://forum.godotengine.org/t/post-mortem-of-my-failed-attempt-to-vibe-code-a-metroidvania-game/137567)). So the honest answer to "is Godot development an abstract, fixed workflow?" is: the *checking* is fixed and reusable, while the *making* (design, content, art direction, feel) stays genre-specific and human-led. Generic skill packs that script the making, such as studio role-play, seven-stage pipelines or "27 genre blueprints", automate the part with the least evidence behind it.

This project sits in the best possible position for the reusable part. A grid-based Bomberman-like has discrete rules that are cheap to make deterministic without engine physics. A remake also has an oracle: the original SWF, run in the seeded Ruffle reference player, turns UI, art and timing from questions of taste into comparison questions. Projects that decompiled games with agents report the same effect: a byte-match check against the original binary removed the need for an agent reviewer step ([momo5502](https://momo5502.com/posts/2026-10-09-game-decompilation/)). An AS3-to-GDScript port cannot match bytes, but display-list and focus-dump traces serve the same role. What the oracle cannot settle is cross-renderer pixel differences, feel on a phone, and the Douyin variant's new art. Those stay with the owner.

## Prioritized recommendations for bomb-it-5

The 2026-11-02 restart wrote the right rules: `docs/development.md` as the only status document, capped at a page; goldens as display-list dumps with captures kept local in `.scratch/`; logic closes on automated checks while UI and art close only on owner confirmation. On `main` (last moved 2026-11-04) those rules hold: `tests/goldens/` is about 3.4 MB. But the working branch `claude/kind-johnson-vp2tp9`, unmerged for 19 days, has already drifted: `docs/development.md` there is 950 lines, and it commits 225 golden files totalling about 193 MB (single character-select timelines of 4–5 MB, gameplay frame dumps of ~125 KB each). The remaining risks are enforcement, golden size before that branch merges, and the missing playground. The order below puts the cheapest high-leverage items first.

| Priority | Action | Problem addressed | Why |
| --- | --- | --- | --- |
| 1 | **Enforce the owner gate in tooling, not prose.** Give UI and art tickets a "ready for owner review" state per the triage labels. Add a check (GitHub Action or agent hook) that reopens or blocks closing a UI or art issue unless the owner closed it or commented an acceptance. Have the comparison loop post its node-diff and SSIM summary plus three or four PNG frames to the issue. | Self-referential closure | Every surveyed plugin makes agents more autonomous, and none adds a human gate. The rule failed before because it was only text. |
| 2 | **Keep the node-diff comparison loop as the primary check; do not adopt a tool's screenshot comparison in its place.** Extend it per checkpoint with per-frame state traces for gameplay (focus dump each tick, first-divergence report), following GameLogicBench and Riot. | Slow pixel loops | Structured state beats both vision judges and terminal-only checks. No off-the-shelf tool reads SWF references. |
| 3 | **Add Erodenn/godot-mcp-runtime to the Claude Code setup for local runs only.** Use it for single-frame screenshots, `get_ui_elements` rectangles and input injection while developing. Vet it first per the dependency rules, and adopt godot-bridge's lessons: no `-d` by default, always `--quit-after`, call the real Godot binary rather than a shim. Do not commit an `eval`-capable autoload; if one is ever needed, exclude it from every export preset, including Douyin. | Agent cannot see the game | Same perception as godot-bridge, matches the 4.5 pin, and leaves `project.godot` untouched. hi-godot/godot-ai needs 4.7+. |
| 4 | **Use Godot's own embedded Game view (4.4+) as the owner's live playground.** It offers runtime node selection into the Inspector and suspend with frame stepping ([docs](https://docs.godotengine.org/en/4.7/tutorials/editor/game_embedding.html)). Add a small debug scene per checkpoint that loads the generated screen beside the reference capture, with a frame slider driven by the case's stepped frame count. | No live playground | No plugin offers an owner-facing playground. The engine already has one, and a side-by-side scene costs little. |
| 5 | **Treat GitHub Issues as the cross-session memory and keep docs as they are.** Start each session from the current checkpoint issue, record decisions as issue comments, and do not install broad skill packs (dsh-godot-skill, studio role-play, genre blueprints). If anything, write one short project skill for running `tools/compare.sh` and the known headless traps (Xvfb for pixels, GUT exit-0 failures, `--import` before tests). | Doc bloat, lost context | Generic Godot knowledge is already saturated in frontier models, and generic workflows conflict with "translate, don't reinvent". |
| 6 | **Shrink the goldens before `claude/kind-johnson-vp2tp9` merges.** Store timelines as per-node changes, gzip them, keep keyframes rather than every frame, and move large goldens to Git LFS or an artifact store, leaving case definitions and hashes in git. Once 193 MB lands on `main` it stays in history; afterwards only a shallow or partial clone (`--filter=blob:limit=...`) or a disruptive history rewrite helps. | 193 MB of goldens | It is still cheap to fix now, on an unmerged branch. |
| 7 | **Revisit at checkpoint 6 (phone and touch).** Feel on a device is the one area where neither the oracle nor any tool helps. Plan owner play sessions instead of agent playtesting there. | Feel and art on phone | GUI playtesters are weakest on real-time timing and small UI. |

## Conclusion

The research turns a tooling question into a governance question. Godot agent plugins have converged on the same set of eyes and hands (screenshot, input, scene tree, eval) across dsh, Claude Code, Codex and Cursor. They are now a commodity worth having, but they raise the risk this project already paid for: an agent that can see its own output becomes more confident that the output is correct. The benchmarks show the decisive variables are what the agent is checked *against* and who signs off. Scaffold choice alone moved one model from 26% to 44% on GameLogicBench, and executable state checks beat vision judges by about 14 points on SWE-Game.

For bomb-it-5, the original game is a stronger asset than any plugin. Few agent projects have a seeded, steppable reference player that defines what "right" means for every node and frame. The remaining work is to make the owner gate impossible to skip, add a cheap runtime MCP for the agent and the engine's own Game view for the owner, and resist generic workflow packs. Those packs automate the creative half of game development, the half a faithful remake has already settled.
