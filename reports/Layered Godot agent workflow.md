# Fix the checks, not the craft

Godot game development with AI agents can be treated as a reusable workflow across genres, but only one layer of it is reusable. That layer is a verification and session discipline: a headless launch gate, deterministic scenario boots, replayed input traces, per-tick state assertions, and handoff notes that survive between sessions. What the game should be, what it should look like and whether it feels right have to be chosen per genre or done by hand. The primary sources behind this answer are now checked. GameCraft-Bench's 41.46% top score and GameDevBench's 53.8% are both confirmed, but the GameDevBench headline belongs to Gemini 3 Pro, not GPT. Its "about ten points from screenshots" is the best case (+10.9), not the typical one. The "68.44%" that looked like a stray figure is the top of GameCraft's later leaderboard (Claude Code with Opus 5). Per-genre data exists in only one Godot benchmark, GameCraft-Bench. It shows a 30-point spread between the best and worst families. Agents lose most on families whose state must be shown through UI (card, idle, racing, rhythm) and on art in systems-heavy games. The jams agree. The few Godot entrants who published workflows, and the Vibe Jam winners, kept design, art direction, level layout, playtesting and sign-off for the human, and handed code and tooling to agents. For bomb-it-5 this is good news. A faithful remake with a seeded reference player has an oracle where other projects need taste. The project's earlier failures (self-certified UI and art, 193 MB of goldens, doc bloat, lost context) all happened in the layers that should never have been automated or allowed to grow.

Two corrections change the argument, not just the decimals. The feedback gain varies with the model and can be negative, so a vision loop is a tool that helps some agents, not a fixed improvement. ## Godot jam entrants and Vibe Jam winners converge on one division of labour

First-hand Godot write-ups from placed AI-jam entrants are scarce. Most entries only list their tools. Two placed Godot entries left real records, both from Slapjam, a 2026 AI game jam. **Keep It Crispy** won Slapjam #1 (1st of 141), and **Shrinestone** placed 3rd of 211 in Slapjam #2 ([Slapjam #1](https://slapjam.ai/jams/slapjam-1/); [Slapjam #2](https://slapjam.ai/jams/slapjam-2/)). Both used Claude Code (Opus 5.5) on Godot 4.7 for code. A second model, Codex or GPT image generation, made the 2D art. Blender driven by Python scripts made the 3D models, so "any of them can be changed and rebuilt in seconds" ([Keep It Crispy devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight); [Shrinestone page](https://innollia.itch.io/shrinestone)). Neither named a Godot MCP server. The Slapjam #2 winner, Speed Slash, credits only "Godot" and Claude ([game page](https://megumih.itch.io/speed-slash)). The Micro Jam winners Ziva cites, Fire keeper and Follow the Wheat, are known only through the vendor's blog. One quote there says Ziva "saved my life during those debugging sessions" ([Ziva blog](https://ziva.sh/blogs/godot-game-jam-winners)).

The two detailed accounts differ in what they fixed in advance. Keep It Crispy fixed almost nothing. It was a one-day build steered by a 3D artist who "directed and playtested" on an iPhone, saying what felt wrong, and "it got fixed, often within minutes". Its failures were all platform failures, not code structure. Motion sensors worked only over https and not inside the itch iframe. Flame sprites drew black circles in the phone web renderer. The first Android build was unplayable until graphics tiers were added ([devlog](https://juslangit.itch.io/keep-it-crispy/devlog/1683334/how-i-built-a-dragon-raid-in-one-day-with-ai-and-why-tilt-on-iphone-was-the-boss-fight)). Shrinestone fixed a harness. A `CLAUDE.md` defines a Discord-driven worker bot that commits, pushes and replies with a play link ([CLAUDE.md](https://raw.githubusercontent.com/innollia/pai-games/main/CLAUDE.md)). A versioned README, at v27 by submission, holds a handoff section and an "open user complaints, do first" list. It also has a section headed **"Decisions made by the user (don't ask again)"**. A headless smoke test, `--headless --fixed-fps 60 -s tools/smoke.gd`, runs before every push, next to scripted scenes for cliffs, forks, warps and frame rate per zone. The itch upload stayed with the human ([README](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/README.md)). Its art log records how the improvised parts failed. Nested Codex texture calls failed ten times, and GPT shifted textures off their UV layouts until a Python script re-fit them ([ART_LOG](https://raw.githubusercontent.com/innollia/pai-games/main/games/speed_tofu/submit/boulder/ART_LOG.md)).

Outside placed entries, Godot post-mortems repeat the same failures. A GMTK 2026 entrant's agent "decided to throw the engine out the window". It put the whole game in a **1,500-line `main.gd` that builds 3D geometry at runtime**, so the level could not be edited in the editor. A weaker fallback model "only cared that the code compiled" ([Iskamag devlog](https://iskamag.itch.io/chrono/devlog/1608657/to-vibe-a-gamedev-a-first-experience)). A godot-mcp user found that `validate_script` checks syntax only. It misses nonexistent methods and wrong signal signatures, and balance done "by theory, not feel" missed what "a 30-second playtest by a human would reveal instantly" ([saschb2b.com](https://saschb2b.com/blog/godot-mcp-ai-game-creation)). Solo developers report context loss: "by day 3 … code that contradicted systems built two sessions ago". The fix they settled on was per-feature specs and "build one, test it in Godot, verify it works, then move to the next" ([Mormon Trail devlog](https://russperry.itch.io/the-mormon-trail-rpg/devlog/1133249/dec-26-devlog)). One developer abandoned an RTS after losing "complete touch with the underlying code" ([dev.to](https://dev.to/datadeer/part-1-building-an-rts-in-godot-what-if-claude-writes-all-code-49f9)). No 2025–2026 account reported `.tscn` corruption, broken node paths or Godot 3/4 API confusion first-hand.

The Vibe Jam winners worked the same way at a larger scale, and every podium game was Three.js, not Godot. Of 945 entries in 2026, 21 were Godot. One of them, Almost Surgery, won the "Most Cursed" special prize ([vibejam.com](https://vibejam.com/)). The 2025 Gold winner spent 65 hours and €72. He drew the map by hand in Illustrator, had the AI write converters between the editor format and the game, and **restarted the project from an empty repo four times** before the car physics worked, because LLMs "struggle with … spatial orientation, axes, and directions" ([Cassovia Code](https://cassoviacode.com/i-tried-vibe-coding-how-i-created-gta-with-artificial-intelligence/)). The 2026 winner built his capybara game in 15 days with Claude Code, Tripo, Suno and ElevenLabs. He reports spending "most of my time brainstorming, planning, and playing rather than generating code". He used a fresh session per feature, one long-running session for bugs, and 2–3 parallel sessions on separate code areas (via [Wccftech](https://wccftech.com/ios-developer-made-capybara-game-using-vibe-coding-and-won-25000/)). He named "the polish of the game and the artistic part" as the hardest part ([X](https://x.com/leocooout/status/2067423255770857709)). Other entrants converged on letting the AI "create an editor so you have full control" instead of prompting maps ([X](https://x.com/jasperdeboer/status/2044682969030267101)). The organiser credited the winner's "effort gone into the details" ([X](https://x.com/levelsio/status/2067437528320512144)).

| | Godot AI-jam entrants (Slapjam, Micro Jam) | Vibe Jam winners (Three.js) |
|---|---|---|
| Coding agent | Claude Code (Opus 5.5); Ziva in the Micro Jam bracket | Cursor + Sonnet 3.7 (2025); Claude Code, Codex (2026) |

The common pattern is clear even from a thin base. Agents wrote all the code and the tooling that generates content. Humans kept the spec, the spatial layout, the art direction and the judgment of feel. The verification that worked was runtime: headless smoke tests, scripted scenes, the agent driving the game, or a human on the target device. Two counterweights apply. Winners were experienced developers putting in sustained effort, in a field where most entrants "never made a game before" ([levels.io](https://levels.io/winners-of-the-2025-vibe-code-game-jam)). And by 24 Nov 2026, 42% of 2025 games were offline ([vibejam.com/api](https://vibejam.com/api)). Tooling did not lift the median entry in Ziva's bracket either.

## Only GameCraft-Bench measures genre, and it spreads 30 points

Per-genre data is rarer than the benchmarks' framing suggests. **GameCraft-Bench is the only Godot benchmark that reports scores by genre.** GameDevBench classifies its tasks by skill (gameplay, 2D, 3D, UI) and by editor type. SWE-Game spans 13 gameplay categories, GameLogicBench 12 genres and CEGame-Bench a genre chart, but none of the three publishes per-genre scores. GameLogicBench argues on purpose that "a genre with no task is not a gap, whereas a capability with no task is" ([arXiv 2609.21562v2](https://arxiv.org/html/2609.21562v2)). Outside Godot, only OpenGame (Phaser) gives a genre table: intent alignment of 76.8 for platformers, 71.4 for top-down shooters, 66.5 for arcade, 58.2 for strategy and 52.6 for puzzle/UI ([arXiv 2604.18394v2](https://arxiv.org/html/2604.18394v2)).

The category scores explain more than the overall ranking does. **Functional Visuals collapses in families whose state must be read from UI.** Opus-4.7 scores 18.48 on visuals in card games, 23.12 in idle, 23.15 in racing and 24.70 in rhythm. GPT-5.5 hits 90.83 on idle mechanics but 28.12 on idle visuals. Art lags most in systems-heavy families: Opus scores 24.69 for Tycoon art and GPT-5.5 scores 17.45 ([Table 6](https://arxiv.org/html/2606.17861)). Platformer, the "continuous control and collision" family and the largest one, sits in the bottom half for every strong agent. These rankings are fragile. Families of four or five tasks produce both the best and the worst scores. The paper gives no per-family confidence intervals. And its human check found the GPT-5.5 judge most permissive on Idle (+8.76 over humans), so part of Idle's lead is judge inflation ([§5.2, Table 5](https://arxiv.org/html/2606.17861)).

The newer models erode the pattern. On the site's later leaderboard, Opus 5 scores 70.11 on Art against Opus-4.7's 36.86, but the site gives no per-family breakdown and does not say whether the protocol changed ([site](https://tongxuluo.github.io/gamecraft-bench-website/)). The per-skill split survives in GameDevBench: averaged over eight agents, gameplay logic scores 51.4%, 3D 38.4%, 2D graphics and animation 33.0% and UI 32.0% ([arXiv v2 §4](https://arxiv.org/html/2602.11103v2)). Across both benchmarks, then, genre matters mostly through how much of the game is presentation and readable UI, not through the rules. No benchmark covers ports from Flash or any other non-Godot original. The nearest is SWE-Game's Godot-to-Unity task, where Opus5 scored 90.53 on structure, 70.66 on mechanics, 65.88 on playability and only 58.40 on visuals ([arXiv 2609.33678v3](https://arxiv.org/html/2609.33678v3)).

## A three-layer workflow, and where it stops working

The evidence supports a workflow with one fixed layer, one chosen layer and one human layer. The fixed layer is fixed because each element is either genre-blind in the benchmarks or recurs as a fix in every write-up.

**The fixed layer, for every genre, is a runtime contract and a session discipline.** Every commit must pass a launch gate: `godot --headless --path … --quit-after N` exits cleanly, with logs scanned for errors. GameCraft scores a project zero if it fails to launch ([arXiv Appendix A](https://arxiv.org/html/2606.17861)), and CEGame shows that Godot's runtime-only errors make this gate matter more than on Unity. Every game boots named states deterministically, through a `-- --scenario <id>` flag with a seeded RNG. Behaviour is checked by replaying JSON input traces and asserting on engine state **at every tick, not only at the end**, because terminal-only checks let 35.4% of injected faults through ([GameLogicBench](https://arxiv.org/html/2609.21562v2)). Executable state checks rank above pixel comparison, and pixel comparison ranks above a vision-model judgment (92.59% against 78.41% in [SWE-Game](https://arxiv.org/html/2609.33678v3)). Screenshots and video stay available as the agent's own debugging aid, never as acceptance. The rules forbid one-script games: real scenes, typed GDScript and a semantic check beyond `validate_script`. Sessions follow the Shrinestone and capybara pattern. Use a fresh session per feature with a plan step and one verified increment at a time. Keep a single short handoff file with three lists: open owner complaints first, decisions the owner made that must not be reopened, and what changed. Spec files that the human writes and the agent cannot edit are the ground truth ([dev.to](https://dev.to/datadeer/part-1-building-an-rts-in-godot-what-if-claude-writes-all-code-49f9)). Headless traps are written down once: Xvfb is needed for pixels, always pass `--quit-after`, and never use `-d` by default ([godot-bridge CHANGELOG](https://github.com/Smalldy/godot-bridge/blob/main/CHANGELOG.md)).

**The per-genre layer chooses four things: the oracle, the determinism strategy, the asset pipeline and the authoring tool.** The oracle is state predicates for grid, turn, card and strategy games. Physics, racing and platformer games need tolerance-based replays, because Godot float physics is not deterministic ([GDQuest](https://www.gdquest.com/library/glossary/deterministic_simulation)). UI-heavy families need explicit assertions that the state is visible on screen (counter values, card states, timing cues), because that is where GameCraft's visuals scores collapse. Assets come from a 2D image model, from Blender scripts for 3D, or from procedural code, and the choice includes a repair step such as Shrinestone's UV re-fit. Spatial content (maps, tracks, open worlds) goes into an editor the human drives, either Godot's own or an AI-built one, not into prompts; every jam winner who fought spatial reasoning ended up there. Platform targets add their own export tests: mobile web needs https, iframes and graphics tiers.

**The hand layer is design, ground truth, art direction, feel and sign-off.** Humans write the spec and scope, author or approve spatial layouts, choose generated art and audio, playtest on the real device, accept or reject each screen, and release. They also step in for the 60-second manual fix that would take the agent a long back-and-forth ([top3d.ai](https://www.top3d.ai/learn/claude-godot-mcp-3d-game)). Even the tool vendors concede this: Ziva's playtest agent "does not tell you whether the game is fun" ([Slapjam review](https://slapjam.ai/news/ziva-review-godot-ai-agent/)).

The limits are real. The fixed layer catches broken behaviour but cannot rank good behaviour, so it gives no lift on fun, polish or originality, which are exactly what judges rewarded. Its evidence comes from short tasks (GameCraft's agents had 7,200 s) and from a handful of jam write-ups, two of them detailed. Nothing here measures a months-long project. The layer also needs a definition of "right". For original games, the per-tick assertions are only as good as the human's spec. For multiplayer, the workflow needs netcode design and multi-process tests that no Godot benchmark covers. And workflow polish does not replace experience: winners were seasoned developers, and the median AI-assisted entry scored no better than the field.

## What this means for bomb-it-5

bomb-it-5 is close to the best case for this workflow, because its oracle supplies what other projects need taste for. The original SWF in a seeded reference player defines the right state, position, frame and timing for every node. That turns most of the per-genre layer into a solved problem. The oracle is a display-list and state comparison against the reference, and determinism comes from a grid-based simulation that needs no engine physics. As a maze-bomber, the game combines platformer-style real-time collision with strategy-style state readability, the two GameCraft weak spots. This is an analogy, not a measurement, but both weak spots are what the comparison loop checks directly. The earlier failures sit in the other two layers.

Self-certified UI and art was a hand-layer task automated by mistake. The fix is mechanical, not more prose: issues get a "ready for owner review" state that only the owner can close, and the comparison loop posts its node diff and a few frames to the issue. The slow pixel comparison and the 193 MB of goldens put pixels above state, which inverts the fixed layer's ordering. The branch carrying them, `claude/kind-johnson-vp2tp9`, is still unmerged as of 24 Nov 2026. The order should be node and state diffs per tick with a first-divergence report, then SSIM and ΔE on a few keyframes, with captures kept outside git and timelines stored as per-node changes before that branch merges. Doc bloat and lost context had the same root cause. The same branch grew `docs/development.md` to 950 lines while `main` holds it at 204, because one document tried to be the spec, the status and the session memory at once. The fixed layer splits those jobs. The SWF and the evidence records are the ground truth. A short handoff in the checkpoint issue carries owner complaints, owner decisions that must not be reopened, and what changed. A fresh session per feature starts from that issue. Two engine rules also apply: GameCraft-style scenario boots and input traces fit the seeded reference player directly, and the Godot project's own contribution policy means any upstream engine fix found while porting must be written by a human ([contributing docs](https://contributing.godotengine.org/en/latest/development/contribution_rules.html#ai-assisted-contributions)).

## Conclusion

The question "is there a reusable Godot agent workflow?" has a narrower answer than either the skill packs or the sceptics suggest. Reuse lives in the contract the game makes with its checker (launch, boot a scenario, replay inputs, expose state every tick) and in how sessions hand over. It does not live in a scripted pipeline of design, content and polish stages, which is the part with the least evidence and the part winners kept for themselves. Per-genre variation turns out to be mostly a question of how much of the game must be *shown* rather than *computed*. That is why UI-heavy families and art score lowest, and why genre choice matters less than whether an external reference exists.

For bomb-it-5 the implication is to stop treating the comparison loop as a test suite bolted onto a creative process. It is the fixed layer, and the reference player makes it unusually strong. The work left is to keep the hand layer human by mechanism, put state ahead of pixels, and keep memory in the issue tracker rather than in a growing document. On the evidence, the project's earlier difficulties were not a sign that agents cannot port the game. They show what happens when the oracle is not used as the authority.
